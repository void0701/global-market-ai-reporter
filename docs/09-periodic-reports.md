# 09. 週次・月次・年次レポート

最終更新: 2026-11-22

日次レポートに加えて **週次・月次・年次** のレポートを生成する。本ドキュメントはその設計。

---

## 1. 設計の基本方針

### 1-1. 期間レポートは「ニュースを再収集しない」

期間レポートは RSS を再取得しない。**S3 に保存済みの日次解析 JSON を入力にする。**

```
日次: RSS収集 → 重複排除 → AI解析 → data/daily/2026-11-24.json を保存
                                              │
週次:                        5日分のJSONを読む ┘ → AI統合 → weekly/2026-W47.json
                                              │
月次:                        4-5本の週次を読む ┘ → AI統合 → monthly/2026-11.json
                                              │
年次:                        12本の月次を読む  ┘ → AI統合 → yearly/2026.json
```

**これは [05](05-decisions.md) A-23（解析結果の生 JSON も保存する）があって初めて成立します。** 当時は「HTML テンプレート変更時に過去分を再生成できるように」という理由でしたが、結果的に期間レポートの基盤になりました。

### 1-2. 階層的ロールアップを採る

| 方式 | 月次の入力 | 入力トークン | 特性 |
|---|---|---|---|
| **階層的（採用）** | その月の週次サマリ 4〜5 本 | 約 7,600 | 安い。週次の時点で蒸留済み |
| 日次から直接 | 日次 JSON 22 本 | 約 32,000 | 詳細は残るが高い。年次では 365 本=破綻 |

**階層的ロールアップを採用する。** 年次で日次 250 本を 1 回の呼び出しに入れるのは現実的でなく、月次だけ方式を変えると実装が二重化する。全階層で同じ「1 つ下の階層を入力にする」規則に統一する。

**ただし機械集計（統計値）は常に日次の全データから計算する。** AI への入力は階層的に蒸留されるが、数値は欠落させない。これが次の 1-3 につながる。

### 1-3. 「機械集計」と「AI の統合」を分離する

期間レポートは 2 つの部品で構成する。

| 部品 | 生成方法 | 内容 |
|---|---|---|
| **統計サマリ** | **AI を使わない純粋な集計** | センチメント推移、S&P500 の期間騰落率、VIX 推移、判定の分布、予測の的中率 |
| **統合ナラティブ** | Bedrock による統合 | 期間を通じた主要テーマ、何が継続し何が解消したか、次期間の見通し |

分離する理由は 3 つ。

1. **数値を AI に計算させない。** センチメントの平均や騰落率の累積は決定的に計算できる。AI に計算させると誤る可能性があり、検証もできない。
2. **統計サマリを AI への入力に含める。** 集計済みの数値を渡せば、AI は「11月は下落圧力が優勢だった」という事実を取り違えずに記述できる。
3. **AI 障害時も統計だけは出せる。** Bedrock が失敗しても統計サマリ付きのレポートは生成できる。

## 2. 🔴 実行スケジュールの見直し（重要な発見）

### 2-1. 現行設計では週 2 回、空のレポートが生成される

「毎日 07:00 JST」という当初設計を検証したところ、**日曜と月曜の実行は米国市場の取引セッションを 1 つも含みません。**

```
JST実行 → 対象24h窓(ET) → 窓に含まれる取引セッション(ET 09:30-16:00)
──────────────────────────────────────────────────────────
11/23(月) 07:00  →  11/21 17:00〜11/22 17:00  →  ❌ セッションなし
11/24(火) 07:00  →  11/22 17:00〜11/23 17:00  →  ✅ 月11/23
11/25(水) 07:00  →  11/23 17:00〜11/24 17:00  →  ✅ 火11/24
11/26(木) 07:00  →  11/24 17:00〜11/25 17:00  →  ✅ 水11/25
11/27(金) 07:00  →  11/25 17:00〜11/26 17:00  →  ✅ 木11/26
11/28(土) 07:00  →  11/26 17:00〜11/27 17:00  →  ✅ 金11/27
11/29(日) 07:00  →  11/27 17:00〜11/28 17:00  →  ❌ セッションなし
```

**火〜土の 5 回が米国の各取引日に 1 対 1 で対応し、日・月の 2 回は空振りします。** 07:00 JST = 17:00 ET（前日）という時刻設計上、金曜の引け（16:00 ET 金）は土曜 07:00 JST の窓に入り、日曜 07:00 JST の窓（金 17:00〜土 17:00 ET）からは外れます。

空振り回でも「週末のニュース」はあるため完全な無駄ではありませんが、**市況データに前日比が存在せず、分析の中核である「取引への反映」を論じられません。** トークンも消費します。

### 2-2. 推奨スケジュール

| レポート | 実行タイミング | cron（`Asia/Tokyo`） | 回数 |
|---|---|---|---|
| **日次** | **火〜土 07:00 JST** | `cron(0 7 ? * TUE-SAT *)` | 約 22 回/月 |
| **週次** | **月曜 07:00 JST** | `cron(0 7 ? * MON *)` | 約 4.3 回/月 |
| **月次** | 毎月 1 日 07:30 JST | `cron(30 7 1 * ? *)` | 1 回/月 |
| **年次** | 1 月 1 日 08:00 JST | `cron(0 8 1 1 ? *)` | 1 回/年 |
| 日曜 | **実行しない** | — | — |

**月曜 07:00 JST に日次ではなく週次を出すのが、この設計の要点です。**

- 日次としては空振りする枠を、週次レポートに充てる
- 週次は **前週（月〜金の 5 セッション）+ 週末のニュース** を対象にできる
- 米国市場の月曜寄り付きは 23:30 JST なので、**月曜朝に前週の振り返りと今週の見通しを読める**タイミングになる

月次・年次は日次と同日になるため、**07:30 / 08:00 にずらして同時実行を避けます**（同じ Lambda を別スケジュールから別ペイロードで呼ぶ）。

> **副次的な効果: コストが下がります。** 日次を 30 回 → 22 回に減らすことで、週次・月次・年次を追加しても**総額は当初見積もりより安くなります**（§5）。

### 2-3. 「毎日出したい」場合

当初のご指示は「毎日 07:00 JST」でした。日曜・月曜も出す選択も可能です。

| | 火〜土（推奨） | 毎日 |
|---|---|---|
| 日次の回数 | 22 回/月 | 30 回/月 |
| 空振り回 | なし | 週 2 回 |
| 月額（Bedrock） | 約 $6.0 | 約 $7.8 |
| 週末ニュースの扱い | 週次レポートが拾う | 日次が拾う |

**推奨は火〜土。** 週末のニュース（地政学、政策announcement、Fed 高官発言）は週次レポートが「前週 + 週末」としてカバーするため、情報の取りこぼしがありません。

→ **この変更の可否をご判断ください。** 現時点では推奨案（火〜土）で設計を進めます。

## 3. 予測の振り返り（的中率の集計）

期間レポートに**日次予測が当たったかの検証**を入れる。これは期間レポートを「要約の再要約」以上のものにする仕掛け。

### 3-1. 集計方法

日次レポートの `news_analysis` のうち `horizon == "immediate"`（当日〜翌日に効く材料）の `direction` を集約し、**翌取引日の S&P500 の実際の騰落と比較する**。

```
11/24 の日次: immediate 判定が 上昇要因×1、下落要因×3  → ネット「下落」
11/25 の実績: S&P500 -0.8%                            → ✅ 的中

→ 期間内の的中数 / 判定があった日数 を集計
```

`confidence`（高・中・低）で重み付けし、`volatility`（ボラティリティ拡大）判定は方向を持たないため集計対象外とする。

必要なデータはすべて日次 JSON に既に含まれる（`news_analysis` と `market`）ため、**追加の API 呼び出しもデータ取得も不要**。純粋な後処理。

### 3-2. この指標の限界（過大評価しないこと）

**[重要]** この的中率は粗い指標であり、以下の限界があります。レポート上にもこの注意書きを載せます。

| 限界 | 内容 |
|---|---|
| **サンプルサイズ** | 週次は 5 日分しかなく、**統計的にほぼ無意味**。意味を持つのは月次（約 22 日）以降、信頼できるのは年次（約 250 日） |
| **方向のみ** | 騰落の「幅」を見ていない。-0.05% も -3% も同じ「下落」として扱う |
| **帰属できない** | 複数ニュースの合成判定と指数全体の動きを比較しているだけで、「このニュースがこの動きを起こした」とは言えない |
| **交絡要因** | 判定に含まれない要因（海外市場、需給、月末リバランス等）で動くことが常にある |

**運用方針:**
- **週次: 記録のみ**（数値は出すが判断材料にしない。「参考値」と明記）
- **月次: 傾向を見る**（偏りが続いていればプロンプト改善の手がかりにする）
- **年次: 主要な評価指標の 1 つとして扱う**

> この指標の本来の価値は「当たったか」ではなく、**AI の判定に系統的な偏り（常に強気、確度「高」の乱用など）がないかを検出すること**にあります。的中率が 50% 前後でも、偏りがなければ分析として健全です。

### 3-3. ⚠️ ベンチマークを必ず併記する

**的中率を単独で出してはいけません。** S&P500 は長期的に上昇バイアスがあるため、**「常に上昇要因と判定する」だけで 50% を超えます**。

| 併記するベンチマーク | 意味 |
|---|---|
| 常に「上昇」と判定した場合の的中率 | 上昇バイアスの大きさ |
| 常に「下落」と判定した場合の的中率 | 上記の裏 |
| AI の的中率 | 上記と比べて初めて意味を持つ |

「的中率 58%」は、常に強気戦略が 55% なら**優位はわずか 3pp** です。ベンチマークなしの的中率は解釈不能なため、レポートには必ず 3 つ並べて表示します。

この計算は保存済みデータから**後から再計算できる**ため、スキーマ変更は不要です（[10 §4](10-schema-capabilities.md) Tier C）。

### 3-4. 現状は `immediate` しか評価できない

**`short_term`（2〜5日）と `long_term`（数週間〜）の判定は、現状まったく検証されていません。** 評価には 3 / 5 / 20 営業日後の S&P500 実績が必要で、これは株価履歴から**後から取得・計算できます**（[10 §4](10-schema-capabilities.md) C1）。

優先度は低いですが、運用 3 か月目以降に追加する価値があります。`long_term` 判定が常に外れているなら、プロンプトの時間軸定義を見直す手がかりになります。

## 4. 出力スキーマ

```python
# src/market_report/models.py（期間レポート部分）

Persistence = Literal["continuing", "resolved", "new"]

class PeriodTheme(BaseModel):
    title: str                      # テーマ名
    narrative: str                   # 期間を通じた経緯
    persistence: Persistence         # 継続中 / 解消 / 期間中に新規発生
    related_dates: list[str]         # 関連する日次レポートの日付

class PeriodStats(BaseModel):        # ★AI生成ではなく機械集計
    sentiment_avg: float
    sentiment_min: int
    sentiment_max: int
    sentiment_series: list[tuple[str, int]]   # (日付, スコア)
    spx_period_change_pct: float
    spx_best_day: tuple[str, float]
    spx_worst_day: tuple[str, float]
    vix_avg: float
    vix_max: float
    tnx_change_bp: float                      # 10年債の期間変化（bp）
    direction_counts: dict[str, int]          # up / down / volatility
    horizon_counts: dict[str, int]            # immediate / short_term / long_term
    forecast_hit_rate: float | None           # 的中率（判定日が0ならNone）
    forecast_sample_size: int

class PeriodAnalysis(BaseModel):
    period_type: Literal["weekly", "monthly", "yearly"]
    period_label: str                # "2026-W47" / "2026-11" / "2026"
    period_start: str
    period_end: str
    stats: PeriodStats               # 機械集計（AIには入力として渡す）
    sentiment_trend_summary: str      # センチメント推移の解釈
    key_themes: list[PeriodTheme]     # 最大5件
    market_recap: str                 # 市況の振り返り
    forecast_review: str              # 予測の振り返り（統計を踏まえた考察）
    outlook: str                      # 次期間の見通し
    report_markdown: str
    x_post_text: str                  # 週次のみ使用
```

**`persistence` フィールドが期間レポート固有の価値です。** 「先週から続いている論点」「今週で解消した懸念」「新たに出てきたリスク」を明示的に分類させることで、日次を並べただけでは見えない流れが出ます。

## 6. 出力ファイルのレイアウト

```
/index.html                      最新の日次レポート
/weekly.html                     最新の週次レポート
/monthly.html                    最新の月次レポート

/reports/2026-11-24.html         日次アーカイブ
/weekly/2026-W47.html            週次アーカイブ（ISO週番号）
/monthly/2026-11.html            月次アーカイブ
/yearly/2026.html                年次アーカイブ

/archive.html                     全レポートの目次

/data/daily/2026-11-24.json      日次の構造化データ
/data/weekly/2026-W47.json
/data/monthly/2026-11.json
/data/yearly/2026.json
```

**週番号は ISO 8601（`2026-W47`）を使う。** ISO 週は月曜始まりで、月曜 07:00 JST に前週を対象として出す設計と整合する。独自の週番号を定義すると年末年始で破綻する。

### アーカイブ一覧ページの構成（[05](05-decisions.md) A-55 を拡張）

4 種類のレポートが並ぶため、種別ごとのセクションに分ける。

```
■ 最新
   日次 2026-11-24 ／ 週次 2026-W47 ／ 月次 2026-11

■ 年次レポート
   2026年

■ 月次レポート
   ▼ 2026年（展開）
       11月  センチメント平均 +1.2 ／ S&P500 +2.3%
       10月  ...

■ 週次レポート
   ▼ 2026年11月（展開）
       W47 (11/16-11/22)  センチメント平均 -0.4 ／ S&P500 -1.1%
   ▶ 2026年10月（折りたたみ）

■ 日次レポート
   ▼ 2026年11月（展開）

   ▶ 2026年10月（折りたたみ）
```

`<details>` 要素による折りたたみで **JavaScript 不要**。各行にセンチメントと一言総括を添えて目次として機能させる。

## 7. 実装への影響

### 7-1. Lambda はペイロードで分岐する

同一の Lambda 関数を 4 つの EventBridge Scheduler から異なるペイロードで呼ぶ。

```python
# lambda_handler.py
def handler(event, context):
    report_type = event.get("report_type", "daily")
    dry_run = event.get("dry_run", False)
    return pipeline.run(report_type=report_type, dry_run=dry_run)
```

`pipeline.run()` は `daily` なら RSS 収集から、`weekly` / `monthly` / `yearly` なら S3 からの JSON 読み込みから始める。**スモークテスト（`dry_run: true`）はこの経路をそのまま使えます。**

### 7-2. ⚠️ 日次 JSON のスキーマを今固める必要がある

**これが最も重要な実装上の制約です。**

期間レポートは過去の日次 JSON を読みます。つまり **日次 JSON のスキーマを後から変えると、それ以前に生成した日次データが集計できなくなります。**

したがって:

1. **Phase 1 の時点で日次 JSON のスキーマを確定させる**（期間レポートが必要とするフィールドを含めて）
2. JSON に **`schema_version` フィールドを持たせる**（将来の変更時に移行処理を書けるようにする）
3. 集計側は未知の `schema_version` を**エラーにせず警告してスキップする**（古いデータが混ざっても処理を止めない）

期間レポートが日次 JSON に要求するフィールド:
- `date`, `schema_version`
- `sentiment_score`, `sentiment_summary`
- `news_analysis[]`（`horizon` / `direction` / `confidence` / `headline` / `transmission`）
- **`market`**（`spx_close`, `spx_change_pct`, `tnx`, `tnx_change_bp`, `vix`）← 的中率集計と統計に必須

### 7-3. 期間の境界でデータが欠けている場合の扱い

| 状況 | 挙動 |
|---|---|
| 週次実行時に日次が 5 本揃っていない | **揃っている分で生成する**。欠損日をレポートに明記 |
| 日次が 0 本（運用開始直後など） | **期間レポートを生成しない**。ログに記録して正常終了 |
| 月次実行時に週次が 1 本もない | 同上 |

運用開始直後は当然データがないため、**データ不足を異常としない**。ただし「3 週連続で週次が生成されていない」ような状態は通知対象にする。

### 7-4. Phase 割り当て

| 作業 | Phase |
|---|---|
| **日次 JSON スキーマの確定**（`schema_version` 含む） | **Phase 1（必須。後から変えられない）** |
| 統計サマリの集計ロジック（`PeriodStats`） | Phase 1 |
| 的中率の集計ロジック | Phase 1 |
| 期間レポートの AI 統合 + HTML 生成 | Phase 1（フィクスチャの日次 JSON で検証） |
| 4 本の EventBridge Scheduler | Phase 2 |
| 日次スケジュールの火〜土化 | Phase 2 |
| 週次レポートの X 投稿 | Phase 3（§8） |

**Phase 1 で期間レポートまで実装します。** 入力が S3 ではなくローカルの JSON になるだけで、ロジックは同一です。フィクスチャとして日次 JSON を数本用意すれば完全に検証できます。
