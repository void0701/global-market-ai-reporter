# 07. 準備が必要なもの（ユーザー作業）

最終更新: 2026-11-22

このドキュメントは **ken さん側で用意・操作が必要なもの** のチェックリストです。Claude 側で代行できない作業（アカウント作成、認証情報の入力、支払い方法の登録、MFA 設定など）を Phase ごとに整理しています。

## 役割分担

| Claude がやること | ken さんがやること |
|---|---|
| コードの実装・テスト | **アカウントの作成と支払い方法の登録** |
| Terraform の記述 | **MFA の設定** |
| ドキュメントの作成・更新 | **AWS コンソールでのモデルアクセス有効化** |
| ローカルでの動作確認 | **認証情報（シークレット）の投入** |
| GitHub Actions ワークフローの記述 | **GitHub Environments の必須レビュアー設定** |
| 設計上の選択肢の提示 | **ルート用メールアドレスの用意と MFA 設定** |

> ⚠️ **認証情報は Claude に渡さないでください。** X API のキーや AWS のアクセスキーは、チャットにも、リポジトリ内のファイルにも置かないでください。シークレットは [06 §2-3](06-cicd-and-environments.md) のとおり、ken さんが AWS CLI またはコンソールから直接 Secrets Manager に投入する運用にしています。Claude は値を知る必要がありません。

## Phase 1 に必要なもの

### A-0. 🔑 アカウント作成前に決めること

**AWS アカウントのメールアドレスとアカウント数は、後から変えるのが面倒です。作る前に決めてください。**

#### メールアドレスは私用のものと分けるべきか → **分けるべきです**

理由は 3 つあります。重要度順です。

**1. ルートユーザーのメールアドレス = アカウントの所有権そのもの**

パスワードリセットはそのメールアドレスに届きます。**メールアカウントが侵害されれば AWS アカウント全体を奪われます。** MFA を設定していても、AWS サポート経由のアカウント復旧はメールアドレスと電話番号が鍵になります。

つまり **AWS アカウントのセキュリティは、紐づけたメールアカウントのセキュリティを超えられません。** 私用メールは長年使っていて漏洩リストに載っている可能性があり、フィッシングの標的にもなりやすい。

**2. AWS アカウント 1 つにつきメールアドレス 1 つ（一意制約）**

同じアドレスで 2 つ目のアカウントは作れません。将来 Organizations でアカウントを分ける場合、アカウントごとに別アドレスが必要になります。普段使いのアドレスを消費すると後で困ります。

**3. 通知が埋もれる**

請求アラート、セキュリティ通知、サービス終了予告が私用メールに混ざると見落とします。本システムは**失敗通知もメールで受ける設計**（[05](05-decisions.md) A-53）なので、なおさらです。

#### メールアドレスの選択肢

| 方式 | 所有権の分離 | アドレスの追加 | 評価 |
|---|---|---|---|
| **専用の新規メールアカウント** | ✅ | ✅ | **◎ 推奨** |
| 独自ドメインのメール（`aws@example.com`） | ✅ | ✅ | ○（下記の注意あり） |
| 既存 Gmail のサブアドレス（`name+aws@gmail.com`） | ❌ | ✅ | △（下記の落とし穴） |
| 私用メールそのまま | ❌ | ❌ | ✗ 非推奨 |

> ### ⚠️ サブアドレス（`+aws`）の落とし穴
>
> `yourname+aws@gmail.com` は AWS 上は**別のアドレスとして扱われる**ため、複数アカウントを作る用途には使えます。
>
> **しかし受信箱は同じです。** 元の Gmail アカウントが侵害されれば AWS アカウントも道連れになり、**「所有権の分離」という目的をまったく果たしません。** アドレスの数の問題は解決しますが、セキュリティの問題は解決しない、という点を混同しないでください。

> ### ⚠️ 独自ドメインのメールの注意
>
> `aws@yourdomain.dev` のような独自ドメインのアドレスは分離の観点では優れていますが、**ドメインの更新を忘れるとメールが受け取れなくなり、AWS アカウントの復旧ができなくなります。** これは実際に起きる事故です。
>
> 自動更新を必ず有効にする自信がなければ、無料のメールサービスで専用アカウントを作る方が安全です。

#### ルート用と通知用は別物として考える

混同しやすいので整理します。**2 種類のメールアドレスが登場します。**

| 用途 | 推奨 | 普段見るか |
|---|---|---|
| **ルートアカウント用** | 専用の新規アドレス。**そのメールアカウント自体にも MFA 必須** | 見なくてよい（重要通知のみ） |
| **運用通知用**（SNS → 失敗通知） | **普段見るアドレスでよい** | 毎日見る |

ルート用を普段見ないアドレスにするのは問題ありません。請求アラートや重要通知は、別途 IAM Identity Center のユーザーや SNS で普段見るアドレスに転送できます。

> **メールアカウント自体の MFA を忘れないでください。** 専用アドレスを作っても MFA を付けなければ、そこが最弱リンクになります。せっかくの分離が無意味になります。

---

#### AWS アカウントは 1 つでよいか → **このプロジェクトには 1 つで十分です**

ただし **「1 つでよい」と「他の用途と混ぜてよい」は別の話**です。混同しないでください。

**(a) このプロジェクト内では 1 アカウントで十分**

[05](05-decisions.md) A-27 で「単一 AWS アカウント + リソース分離」を確定済みです。`dev` と `prod` は以下で厳格に分離されており、アカウントを分ける必要はありません。

| 分離の手段 | 内容 |
|---|---|
| IAM ロール | dev と prod で別。prod ロールは dev のワークフローから引き受け不可 |
| Terraform state | 別ファイル（`dev/` と `prod/` で key を分離） |
| リソース名 | 全リソースに `${project}-${env}-` プレフィックス |
| **シークレット** | **prod のみに存在**（dev からの誤投稿が構造的に不可能） |

アカウント分離の主な価値は「本番データへの意図しないアクセスの防止」ですが、**本システムに保護すべき本番データは存在しません**（扱うのは公開ニュースと公開レポート）。保護対象は X API の認証情報 1 点に集約され、これは Secrets Manager の権限設計で守れます。Organizations の運用負荷に見合いません。

**(b) ただし、既存の別用途アカウントは流用しないでください**

仕事用や他プロジェクトの AWS アカウントを持っていても、**このプロジェクト専用に新規作成する**ことを推奨します。

| 流用した場合の問題 |
|---|
| **課金が分からなくなる** — Bedrock の消費が他の費用に埋もれ、[03](03-cost-and-tokens.md) の実測検証ができない |
| **IAM が複雑化する** — 既存のロールやポリシーと干渉し、最小権限の設計が崩れる |
| **事故の影響が波及する** — Terraform の誤 apply が他のリソースに及ぶ |
| **Budgets アラートが機能しない** — 閾値 $20 が他の用途の費用で埋まる |

> つまり「**専用のアカウントを 1 つ作る**」が答えです。「1 つでよい」＝「何かと共用してよい」ではありません。

**(c) 将来アカウントを分けたくなったら**

Terraform を環境別ディレクトリ構成にしてあるため（[06](06-cicd-and-environments.md) §2-2）、provider の `assume_role` 設定を差し替えるだけで移行できます。**今の構成がそのまま移行の土台になります。**

### A-1. ⚡ アカウント作成直後にやること（この順番で）

**アカウントを作った直後はルートユーザーでログインしている状態です。これが最も危険な状態なので、まずルートを封印します。**

| # | 作業 | 誰で | 所要 |
|---|---|---|---|
| 1 | **ルートユーザーに MFA を設定** | ルート | 5分 |
| 2 | **ルートのアクセスキーが無いことを確認**（あれば削除） | ルート | 1分 |
| 3 | **アカウントエイリアスを設定**（サインイン URL が分かりやすくなる） | ルート | 1分 |
| 4 | **請求アラートを有効化**（請求ダッシュボード > 請求設定） | ルート | 3分 |
| 5 | **AWS Budgets で月額 $20 のアラート**（通知先は普段見るアドレス） | ルート | 5分 |
| 6 | **IAM Identity Center を有効化**し管理者ユーザーを作成 + MFA | ルート | 15分 |
| 7 | **ルートからサインアウト。以後は使わない** | — | — |
| 8 | **Bedrock のモデルアクセスを有効化** | Identity Center のユーザー | 5分〜**数日** |

> **6 の注意:** IAM Identity Center のインスタンスはリージョンに紐づきます。**`ap-northeast-1`（東京）で有効化**してください。後から変更するにはインスタンスの削除・再作成が必要です。

> **4・5 の注意:** 請求情報へのアクセスはデフォルトでルートに限定されています。Identity Center のユーザーで請求を見たい場合は、ルートで「IAM ユーザー/ロールによる請求情報へのアクセス」を有効化してください。

### A-2. ⚠️ Bedrock のモデルアクセスはリージョンごと

**最も起きやすい事故です。**

モデルアクセスの有効化は**リージョン単位**で行われます。コンソールは既定で前回選択したリージョン（しばしば `us-east-1`）を開くため、**別リージョンで有効化して「有効にしたのに動かない」となるケースが典型的**です。

- [ ] AWS コンソール右上のリージョンが **「アジアパシフィック (東京) ap-northeast-1」** になっていることを確認
- [ ] **Amazon Bedrock > モデルアクセス** を開く
- [ ] **Claude Opus 5** へのアクセスをリクエスト／有効化

**Opus 5 が即座に使えない場合は Claude Sonnet 5 を有効化してください**（全顧客にオープン）。承認待ちで開発は止まりません。

```bash
.venv/bin/market-report run --model anthropic.claude-sonnet-5
```

### A-3. ✅ 設定できたかを 1 コマンドで検証する

```bash
.venv/bin/market-report doctor
```

以下をまとめて確認します。**どのモデルが実際に使えるか**まで判定するため、「有効化したつもり」の取りこぼしを検出できます。

| 検証項目 | 内容 |
|---|---|
| ローカル環境 | Python / SDK / 出力ディレクトリ |
| AWS 認証 | 認証情報の所在、**使用リージョン** |
| **Bedrock** | **候補 3 モデルそれぞれにアクセスできるか**（極小リクエストを 1 回ずつ） |
| 外部データ | RSS 11 本の応答、市況取得、基準日の解決 |

> Bedrock への検証リクエストは `max_tokens=4` の極小呼び出しです。**3 モデル合計で $0.001 未満**です。
> AWS に触れずに確認したい場合は `--quick` を付けてください。

### B. 日常作業用の AWS 権限

ローカルから AWS を操作するための認証方法。**セキュリティ重視の方針（[05](05-decisions.md) A-6）に沿うなら下段を推奨します。**

| 方式 | 推奨度 | 備考 |
|---|---|---|
| IAM ユーザー + アクセスキー | △ | 長期有効なキーが `~/.aws/credentials` に平文で残る |
| **IAM Identity Center（旧 AWS SSO）** | **◎ 推奨** | `aws sso login` で一時credentialsを取得。ディスク上に長期キーが残らない |

- [ ] **IAM Identity Center を有効化**し、管理者権限のユーザーを作成
- [ ] そのユーザーに **MFA を設定**
- [ ] ローカルで `aws configure sso` を実行してプロファイルを設定

IAM Identity Center は初回セットアップが IAM ユーザーより少し手間ですが、**アクセスキーをディスクに置かずに済む**という明確な利点があります。今回の方針に最も合致します。

> IAM ユーザー + アクセスキーで進める場合も動作に支障はありません。その場合は最小権限のポリシーを付け、キーを定期的にローテーションしてください。

- [ ] **Claude Opus 5** へのアクセスをリクエスト／有効化する

## Phase 2 に必要なもの

### F. 通知先

- [ ] **失敗通知を受け取るメールアドレス**（通知手段はメールで確定 → [05](05-decisions.md) A-53）

SNS トピックにメールアドレスを登録すると、**AWS から確認メールが届き、リンクをクリックするまで通知が有効になりません**。この確認操作は ken さんが行う必要があります。

Slack で受け取りたい場合は、その旨お知らせください（[00](00-open-items.md) §2-2）。

### G. 独自ドメイン【当面は不要】

**Phase 2 では CloudFront のデフォルトドメイン（`dxxxxxxxx.cloudfront.net`）で運用する方針が確定しています**（[05](05-decisions.md) A-52）。この段階で用意するものはありません。

構成が固まってから移行する際に必要になるもの:

- [ ] ドメインの取得（候補・レジストラ比較は [00 §2](00-open-items.md)）
- [ ] レジストラは **Route 53 を推奨**（Terraform と認証情報を AWS 1 系統に閉じられる）

> セキュリティ重視の方針に沿うなら TLD は **`.dev` / `.app`** が候補です。この 2 つは HSTS プリロードリストに TLD 単位で登録されており、ブラウザが HTTP アクセスを一切許可しません。

### H. GitHub Actions の設定

Terraform の bootstrap（[06 §2-4](06-cicd-and-environments.md)）を実行した後に必要な GitHub 側の設定:

- [ ] **GitHub Environments に `prod` を作成**
- [ ] `prod` 環境に **必須レビュアーとして自分を設定**

これが prod デプロイの承認ゲートになります（[05](05-decisions.md) A-42）。この設定を入れないと、OIDC の `sub` 条件が一致せず prod デプロイが IAM レベルで失敗します。**つまり設定漏れがあっても事故にはならず、デプロイできないだけです。**

> GitHub Secrets への登録作業は **ありません**。OIDC を使うため、アクセスキーを GitHub に保存する必要がない設計です（[05](05-decisions.md) A-39）。

## Phase 3 に必要なもの

### I. X（旧 Twitter）アカウント

- [ ] そのアカウントに**電話番号を登録** — Developer 登録の要件になることが多い **[要確認]**

### J. X Developer アカウントと App

- [ ] **X Developer Portal** で Developer アカウントを登録
- [ ] **App を作成**
- [ ] **プランを選択**（Free / Basic / Pro）→ 有料プランの場合は支払い方法の登録

**[要確認]** X API のプラン体系・投稿上限・料金はこちらで確認できていません。必要量は月 60 投稿です（[00](00-open-items.md) §3-2）。

### K. X の認証情報の取得 ⚠️ ハマりどころあり

**`POST /2/tweets`（投稿）には「ユーザーコンテキスト」の認証が必要です。** App 専用の Bearer Token では投稿できません。**[要確認: Portal の UI は変更される可能性があります]**

必要な認証情報（OAuth 1.0a User Context の場合、4 点）:
- API Key（Consumer Key）
- API Key Secret（Consumer Secret）
- Access Token
- Access Token Secret

> ### ⚠️ Access Token を生成する前に、App の権限を「Read and Write」に変更してください
>
> **典型的なハマりどころです。** App の権限がデフォルトの「Read」のまま Access Token を生成すると、**そのトークンは読み取り専用**になり、投稿時に 403 エラーになります。権限を変更した場合は **Access Token を再生成する必要があります**（権限変更だけでは既存トークンに反映されません）。
>
> 正しい順序:
> 1. App の設定で User authentication を有効化し、権限を **Read and Write** に設定
> 2. **その後に** Access Token / Access Token Secret を生成

### L. 認証情報の投入

- [ ] 取得した 4 つの値を **ken さんが直接 Secrets Manager に投入**

```bash
# 値をファイルに書いてから投入し、投入後にファイルを削除する
aws secretsmanager put-secret-value \
  --secret-id s-and-p-prod-x-api \
  --secret-string file://./x-credentials.json

rm x-credentials.json   # 必ず削除
```

> **この作業を Claude や CI に任せない理由:** Terraform で管理すると **state ファイルに平文で記録されます**（[06 §2-3](06-cicd-and-environments.md)）。GitHub Secrets 経由で Terraform に渡す設計も同じ問題を抱えます。人間が 1 回だけ手動で投入するのが最も安全です。
>
> `x-credentials.json` は**リポジトリ内に作らないでください**（`.gitignore` に入れますが、リポジトリ外の一時ディレクトリで作業するのが確実です）。
