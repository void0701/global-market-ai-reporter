### ⚠️ レイテンシ 153 秒 — Lambda のタイムアウトに影響

**実測 153 秒 + RSS/市況取得 約 20 秒 = 約 175 秒**で、余裕が 125 秒しかありません。

タイムアウトを延ばしても課金は実行時間ぶんだけなので、コスト増はありません。

## 1. 1 回の実行で消費するトークン **[試算 — §0 の実測で置き換え済み]**

> 本節は**日次レポート**の試算。週次・月次・年次のトークン内訳は [09 §5](09-periodic-reports.md) を参照。

### 前提とした仮定

| 項目 | 仮定値 | 根拠 |
|---|---|---|
| RSS 生取得件数 | 100〜200 件 | 主要経済 RSS 6〜8 本 × 24 時間分 |
| 重複排除後の投入件数 | **15 件** | 同一トピックのクラスタ化後の代表記事 |
| 1 記事あたりの投入量 | タイトル + RSS summary（本文はクロールしない） | トークン節約のため全文取得は行わない |
| レポート本文の長さ | 2,000〜3,000 文字（日本語） | Web 閲覧用の詳細レポートとして妥当な分量 |
| 思考トークン | 2,000〜4,000（中位 3,000） | Opus 5 は adaptive thinking がデフォルト ON |

### 入力トークン内訳

| 構成要素 | トークン数 |
|---|---|
| system プロンプト（解析指示・時間軸定義・分析方針） | 約 1,500 |
| 出力 JSON スキーマ（構造化出力で送信される） | 約 600 |
| 市況コンテキスト（^GSPC / ^TNX / ^VIX の終値・前日比） | 約 200 |
| ニュース 15 件（タイトル + 要約） | 約 2,100 |
| **入力合計** | **約 4,400** |

### 出力トークン内訳

| 構成要素 | トークン数 |
|---|---|
| 思考トークン（adaptive thinking） | 約 3,000 |
| `news_analysis` 5 件（概要 + 波及メカニズム） | 約 1,500 |
| `report_markdown`（2,000〜3,000 字の日本語） | 約 2,500 |
| `watch_list` | 約 320 |
| `sentiment_summary` | 約 100 |
| `x_post_text` | 約 150 |
| JSON 構造オーバーヘッド | 約 200 |
| **出力合計** | **約 7,800** |

> **重要: 思考トークンは出力として課金される。** 出力トークンの約 4 割が思考分であり、ここが総コストの支配要因になっている。出力単価は入力単価の 5 倍なので、コスト最適化を検討する場合は「入力を削る」より「出力を削る」方が効く（例: レポート本文を短くする、effort を下げる）。

> **`report_markdown` を JSON の文字列フィールドに入れる設計のコスト影響**
> レポート本文を JSON 内に持たせるため、改行などのエスケープ分がわずかに増える。別途 2 回目の呼び出しに分ける案と比較すると、**1 回の呼び出しに統合する方が安い**（入力プロンプトとニュース本体を 2 回送らずに済むため）。よって統合案を採用する。

## 2. モデル別コスト比較 **[試算]**

入力 4,400 / 出力 7,800 トークン、月 30 回実行として計算。単価はファーストパーティ参考値。

| モデル | 入力単価 | 出力単価 | 1 回 | 月額 | 月額（¥150/USD 換算） |
|---|---|---|---|---|---|
| **Claude Opus 5（推奨）** | $5.00/MTok | $25.00/MTok | **$0.217** | **$6.52** | **約 ¥980** |
| Claude Sonnet 5 | $2.00/MTok | $10.00/MTok | $0.087 | $2.62 | 約 ¥390 |
| Claude Haiku 4.5 | $1.00/MTok | $5.00/MTok | $0.043 | $1.30 | 約 ¥200 |

計算式（Opus 5）: `4,400 × $5/1,000,000 + 7,800 × $25/1,000,000 = $0.022 + $0.195 = $0.217`

### リトライ分の上乗せ

`x_post_text` の 140 全角文字超過などで再生成が走るケースを **実行の 15〜20%** と見積もる。**[推定]**

ただし再生成は X 投稿文のみを対象にした軽量な再呼び出しにする（レポート全体を作り直さない）設計とするため、上乗せは **月額の +5% 程度** にとどまる見込み。Opus 5 で月額 **$6.5 → $6.9** 程度。

### 結論

**Opus 5 と Sonnet 5 の月額差は約 $3.9（約 ¥590）。** この差額で分析品質を落とす判断は合理的でないと考える。1 日 1 回のバッチという実行頻度が、上位モデルを選べる余地を作っている。

（逆に言えば、将来 1 日複数回・複数指数へ拡張する場合はこの前提が崩れるため、その時点で再評価する。）

### Secrets Manager を採用【確定 2026-11-22】

| | **Secrets Manager（採用）** | SSM Parameter Store（標準） |
|---|---|---|
| 月額 | **$0.40 / シークレット** | $0 |
| API 呼び出し | $0.05 / 1万回 | 無料 |
| リソースポリシー | **あり** | なし |
| 自動ローテーション | あり（ただし下記参照） | なし |
| KMS 暗号化 | あり（CMK 連携） | あり（SecureString） |

セキュリティ優先の方針により Secrets Manager を採用。ただし**選定理由を正確に記録しておく**:

X API の認証情報は自動ローテーションに対応していないため、**Secrets Manager の代表的な付加価値である自動ローテーションは本件では機能しない**。実質的な採用根拠は **リソースポリシーによる権限の二重化・CMK 連携・CloudTrail 統合による監査性**（SSM Parameter Store にはリソースポリシーがない）。月 $0.40 はこの監査性への対価と位置づける。

強化策の詳細は [06 §3](06-cicd-and-environments.md) を参照。特に **Terraform state に秘密情報を書き込まない** 設計が重要（Secrets Manager を選んでも state 経由で漏れれば意味がない）。

> **API 呼び出し課金は無視できる。** 1 日 1 回の実行では Lambda の実行環境が毎回コールドスタートになりメモリキャッシュは効かないが、`GetSecretValue` は月 30 回程度にとどまる。

### 環境分離によるコスト影響

`dev` / `prod` の 2 環境構成（[06 §1](06-cicd-and-environments.md)）だが、**AWS 側の増分はほぼゼロ**。

| | dev | prod |
|---|---|---|
| Lambda / S3 / CloudFront / Scheduler | 無料枠内 | 無料枠内 |
| Secrets Manager | **作成しない**（投稿事故の構造的防止） | $0.40 |
| KMS キー | `state` 用を prod と共有 | `state` 用 + `secrets` 用 = **計 2 キー $2.00/月** |

**KMS の顧客管理キーは $1.00/月/キー** が発生する **[推定]**。

**用途ごとに 2 キーへ分離することを確定**（[05](05-decisions.md) A-65、月 **$2.00**）。

| キー | 暗号化対象 | 復号を許可するプリンシパル |
|---|---|---|
| `state` 用 | Terraform state（dev / prod 共通） | GitHub Actions のデプロイロール |
| `secrets` 用 | X API 認証情報（prod のみ） | Lambda 実行ロール |

共用すれば $1.00 に抑えられるが、**「鍵の用途を混ぜない」原則を適用して安全側に倒す**方針に従った。実効的な利点は、CI のデプロイロールが X の認証情報を復号できなくなること（state 用キーしか使えない）。月 $1.00 の追加でこの分離が得られる。

> state をさらに dev / prod で分けると 3 キー（$3.00）になるが、どちらも同一の CI 系統が触るため分離の実益が小さく、採用しない。

> `dev` で Bedrock を呼ぶ検証を行うと、その分のトークン課金が追加で発生する。[06 §1-3](06-cicd-and-environments.md) のとおり **日常の反復はローカル `--dry-run` で行い、`dev` での Bedrock 実行は意図的な品質検証時に限る**。

### AWS 側の小計

- **Phase 2 時点: 約 $1.00/月**（`state` 用 KMS キー 1 個。他は無料枠内）
- **Phase 3 時点: 約 $2.40/月**（+ `secrets` 用 KMS キー $1.00 + Secrets Manager $0.40）

## 5. X API のコスト **[要確認]**

**この項目は未検証であり、Phase 3 着手前に確認が必要。**

ユーザー提供の前提として以下を設計に織り込む:

- 投稿にURLを含むと単価が高い → **1 ポスト目はテキストのみ**、レポート URL は自己リプライとしてぶら下げる
- 重複投稿エラー（Error 187）回避 → 投稿文先頭に日付 + 前日 S&P500 騰落率を付与

X API v2 の無料枠・各プランの投稿上限と課金体系は頻繁に変更されており、こちらで正確な数値を確認できていない。**Phase 3 着手時に X Developer Portal の現行プラン表で確認する。** 現時点で金額を見積もらない。

1 日あたりの投稿数は **2 件**（本文 + URL リプライ）、月 60 件。

## 6. コスト監視（Phase 2 で実装）

Bedrock の消費が想定から乖離していないかを検知するため、以下を実装する。

1. **実行ごとのトークン数をログ出力。** `response.usage` の `input_tokens` / `output_tokens` を構造化ログに記録し、CloudWatch Logs Insights で推移を追えるようにする。
2. **AWS Budgets でアラート設定。** 月額 $20 を閾値にメール通知（想定の約 3 倍。異常を検知できる水準）。
3. **Phase 1 でもトークン数と推定コストを標準出力に出す。** 本試算の精度を実データで検証し、本ドキュメントを更新する。

> **本試算は実測で置き換えること。** 上記の数値はすべて仮定に基づく。Phase 1 の初回実行でトークン実測値が得られた時点で、本ドキュメントの第 1 節・第 2 節を実測値で更新する。
